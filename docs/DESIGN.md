# Nagare 設計書

Nagare は、中央サーバーを一切持たないライブ配信アプリである。運用者（作成者）は
サーバーを運営しない。配信者と視聴者のブラウザ同士が WebRTC で直接つながり、
視聴者が中継者（リレー）になることで配信ツリーを形成する。

本書は第一原理から新規に設計した記録であり、実装（`nagare.html`）の判断根拠を残す。

---

## 1. 設計原則

1. **ゼロサーバー**: 運用者が用意するサーバーは存在しない。アプリは単一 HTML
   ファイル（`nagare.html`）であり、静的ファイルとしてどこに置いてもよいし、
   ローカルファイルとして開いても動く。
2. **外部依存ゼロ**: CDN・ライブラリ・フォント等を一切読み込まない。ブラウザ標準
   API（WebRTC、CompressionStream、getUserMedia 等）だけで構成する。
3. **個人データを持たない**: 映像・音声・チャットは端末間を直接流れるだけで、
   どこにも保存・送信されない。シグナリング情報もサーバーを経由しない（§2）。
4. **黙って失敗しない**: 接続失敗・権限拒否・コード不正などは、理由を言葉で表示する。
5. **正直な限界を先に書く**: できないことは §8 に明記する。

## 2. シグナリング（ゼロサーバー方式）

### 2.1 なぜコード交換か

WebRTC の接続には SDP と ICE 候補の交換（シグナリング）が必要だが、方式は標準で
定められていない。通常はシグナリングサーバーを用いるが、それは「運用者がサーバーを
持つ」ことになり原則1に反する。そこで、シグナリング情報そのものを**圧縮した文字列
コード**に変換し、配信者と視聴者がチャット・メール・QR コード等、任意の既存手段で
直接交換する方式を採る。

接続は双方向の2コードで成立する。

1. 配信者が「招待コード」を発行する（Offer）。
2. 視聴者が招待コードを貼り、「応答コード」を発行する（Answer）。
3. 配信者が応答コードを貼ると接続が成立する。

### 2.2 リンク形式

招待コードは URL フラグメント（`nagare.html#i=<code>`）にも載せられる。
フラグメントは HTTP リクエストに含まれないため、ファイルをどこに置いても
コードがサーバーへ送信されることはない。ページは読み込み時にフラグメントを
読み取り、招待欄へ自動入力する（自動接続はしない。貼り付けと同じ扱い）。

### 2.3 コード形式

```
NG1.<base64url>.<crc32>
 │      │          └─ 完全性チェック: 圧縮済みバイト列の CRC32（16進8桁）
 │      └─ base64url エンコードした圧縮済みペイロード
 └─ 形式プレフィックス（"NG" + 形式バージョン "1"）
```

ペイロードは JSON を UTF-8 化し、**deflate-raw** で圧縮したもの。

```json
{
  "v": 1,
  "kind": "offer" | "answer",
  "sdp": "<SDP 全文>",
  "ice": [ { "candidate": "...", "sdpMid": "0", "sdpMLineIndex": 0 }, ... ],
  "meta": {
    "role": "origin" | "relay",
    "depth": 0,
    "name": "<表示名>",
    "createdAt": 1730000000000
  }
}
```

判断根拠:

- **圧縮**: SDP は冗長なテキストで、deflate で概ね 1/3〜1/4 になる。ブラウザ標準の
  CompressionStream を使い、外部依存ゼロを保つ。典型的な招待コードは
  1,200〜2,000 文字程度になる。長いが、コピー＆ペーストとリンク共有には耐える。
- **ICE 候補は SDP と分けて同梱する**: ICE 収集完了後の SDP には候補が埋め込まれる
  が、実装差で漏れる場合があるため、収集した候補を配列でも保持し、受信側で
  `addIceCandidate` する（二重適用は候補文字列で重複排除）。
- **バージョン付け**: プレフィックス `NG1` と JSON 内 `v` の二重で持つ。
  プレフィックスで大半の貼り間違い（別アプリのコード等）を即座に弾き、
  `v` で将来の互換判定を行う。不一致は理由を表示して拒否する。
- **完全性チェック**: CRC32 は暗号学的な認証ではない。目的は「コピーの欠落・
  貼り間違いの検出」であり、改ざん防止ではない（§9 の脅威モデル参照）。
  チェック不一致は解凍前に弾く。

### 2.4 ICE 収集の方針

`iceGatheringState === 'complete'` まで待つのが確実だが、環境によっては数秒〜
十数秒かかる。Nagare は**最大 5 秒**で打ち切り、その時点までに集まった候補で
コードを発行する。候補ゼロの場合は発行せず理由を表示する（接続できる見込みが
ないコードを配らない）。

## 3. 接続の状態遷移

セッション（1対の PeerConnection）は次の状態を持つ。

```
idle ──→ gathering ──→ awaiting-peer ──→ connecting ──→ connected
              │              │               │             │
              └──────────────┴─── fail ──────┴──→ failed ──┘（理由を保持）
connected ──→ closed（相手の切断・自分の終了）
```

| 状態 | 意味 |
|---|---|
| `idle` | 生成直後 |
| `gathering` | SDP 生成と ICE 収集中（コード未発行） |
| `awaiting-peer` | コード発行済み、相手のコード待ち（Offer 側）／接続開始直後（Answer 側） |
| `connecting` | 相手の SDP/ICE を適用し、接続確立を待っている |
| `connected` | ICE 接続かつ DataChannel が開通 |
| `failed` | 失敗。`reason` に理由コードを持つ |
| `closed` | 正常・異常を問わず終了済み |

### タイムアウトと再試行

- **接続タイムアウト 20 秒**: `connecting` に入ってから 20 秒以内に `connected`
  にならなければ `failed`（理由: `connect-timeout`）とする。NAT 相性の悪い
  ペアをいつまでも待たせないため。
- **再試行は自動で繰り返さない**。失敗したセッションのコードは使い回さず、
  利用者が「新しい招待を作る」操作で新しいセッションを作る。理由は、同じ
  コードの再交換は同じ失敗を繰り返すだけであり、状態の見通しも悪くなるため。
  試行回数は画面に表示し、失敗が続く場合の確認事項（TURN の設定、ネットワーク
  の変更）を案内する。
- DataChannel が閉じた、または ICE が `disconnected` から 10 秒復帰しない場合は
  `failed`（理由: `peer-lost`）とし、上流が消えたことを下流へも伝える（§5）。

## 4. 配信ツリー（視聴者リレー）

### 4.1 仕組み

視聴者は、受信中の映像・音声トラックをそのまま新しい PeerConnection の送信
トラックとして再配信できる。これにより視聴者が中継ノードとなり、配信ツリー
（配信者を根とする木）ができる。新しい視聴者は、根からでも途中ノードからでも
招待を受けて参加できる。

### 4.2 上限の既定値と根拠

| 項目 | 既定値 | 変更可能範囲 | 根拠 |
|---|---|---|---|
| 1ノードの子数（fanout） | 3 | 1〜6 | 下記 |
| ツリーの深さ（depth） | 4 | 1〜8 | 下記 |

**帯域の計算**: 既定画質 720p のビットレート上限は 2.0 Mbps。子 3 人へ送ると
上り約 6 Mbps + プロトコル overhead（約1〜2割）で約 7 Mbps。一般家庭の光回線の
上り（実効 30〜100 Mbps 級）なら余裕があるが、モバイル回線や混雑時は厳しい。
「確実に届く」ことを優先し、既定は 3 とした。1080p（4.5 Mbps）を選んだ場合は
子 3 人で約 14 Mbps になるため、UI は現在の画質と子数から推定上り帯域を表示し、
回線に合わせて利用者が調整できるようにする。

**規模の計算**: fanout 3・深さ 4 の理論上の最大視聴者は 3+9+27+81 = **120 人**。
深さ 5 なら 363 人。サーバーなしでこの規模に届くのがツリー方式の価値である。

**遅延の計算**: WebRTC の1ホップはおよそ 50〜300 ms（ネットワーク＋ジッタ
バッファ＋再送）。深さ 4 では末端で約 0.2〜1.2 秒の遅延になる。深さを既定 4 に
抑えるのは、遅延と障害の伝播範囲（途中ノードが落ちると配下全員が切れる）を
実用範囲に収めるため。

### 4.3 上限の判定

- ノードは、自分の深さが上限に達したらリレー招待を発行できない（理由を表示）。
- 子数が上限に達したら新しい招待を発行できない（理由を表示）。
- 招待コードの `meta.depth` に発行ノードの深さ +1 が入り、参加側でも検証する。
  ただしこれは表示と判定のための情報であり、強制力は各ノードの実装に依存する
  （オープンなプロトコル上の限界として §8 に記す）。

## 5. DataChannel プロトコル

各セッションに DataChannel `nagare` を1本張る（Offer 側が生成）。メッセージは
JSON で、種別は次のとおり。

| type | 方向 | 内容 |
|---|---|---|
| `hello` | 双方向 | 表示名と深さの自己紹介 |
| `chat` | 双方向 | チャット本文。`id`（重複排除用）、`from`、`text`、`ts` |
| `state` | 子→親 | 自分の配下の視聴者数（subtree） |
| `audience` | 親→子 | ツリー全体の視聴者数（total） |
| `bye` | 双方向 | 切断の予告。受け取ったノードは配下へ転送し、理由として表示する |

- チャットは受信したセッション以外の全セッションへ転送する（木構造なので
  ループは起きないが、`id` の既読集合で二重表示を防ぐ）。
- 視聴者数: 各ノードは「直接の子数 + 各子から報告された subtree の合計」を
  親へ報告する。根が全体数を集計し、`audience` で全員へ配る。報告は接続時と
  変化時、および 5 秒間隔で行う。
- 不正な形式のメッセージは黙って捨てる（プロトコル違反で接続は切らない）。

## 6. 画質とビットレート

| プリセット | 解像度 | フレーム | 映像ビットレート上限 |
|---|---|---|---|
| 1080p | 1920×1080 | 30 fps | 4.5 Mbps |
| 720p（既定） | 1280×720 | 30 fps | 2.0 Mbps |
| 480p | 854×480 | 30 fps | 900 kbps |
| 360p | 640×360 | 30 fps | 450 kbps |
| 音声のみ | — | — | 64 kbps |

ビットレート上限は送信側の `setParameters` で適用する。実際の送信量は
`getStats` で計測し、画面に表示する（推定ではなく実測）。

## 7. STUN / TURN

- STUN は公開サーバーを既定値とし、利用者が変更できる（1行1サーバー）。
  STUN は自分のアドレスを知るためだけに使い、メディアは経由しない。
- TURN は**用意しない**。必要な利用者は自分で用意した TURN の URL・ユーザー名・
  パスワードを設定欄に入力できる。設定は端末内（localStorage）にのみ保存する。
  TURN を経由するとメディアはその TURN サーバーを中継する（＝そのサーバーの
  運営者には通信の存在が見える）ことを UI に明記する。

## 8. 正直な限界

1. **ルームの自動発見はない**。誰が配信しているかを知る手段は、コードやリンクを
   本人同士で交換することだけである。これは欠陥ではなく、サーバーを持たない
   ことの帰結である。
2. **接続できない NAT の組み合わせがある**。双方が対称型 NAT の奥にいる場合
   など、STUN だけでは接続できず、TURN が必要になる。Nagare はその場合に
   理由を表示するが、自動では解決できない。
3. **招待コードは「鍵」である**。コードを持つ人は誰でも参加できる。参加者の
   認証や追い出し（キック）の仕組みはない。
4. **リレーは品質と遅延を悪化させる**。中継ノードの上り帯域が細れば配下全員の
   画質が落ち、段数ぶん遅延が増える。中継ノードがタブを閉じれば配下は切断
   される（再接続は新しい招待からやり直し）。
5. **ツリー上限は紳士協定である**。コードの `meta` は書き換え可能であり、
   上限を守らないクライアントを技術的に排除する手段はない。
6. **ブラウザを閉じれば配信は終わる**。常駐サーバーがない以上、配信者の
   ブラウザが配信そのものである。
7. 視聴者数の集計は各ノードの自己申告に基づく概数である。

## 9. セキュリティの考え方

- **メディアは WebRTC 標準の DTLS-SRTP で暗号化**される。平文で流れることはない。
- **招待コードに含まれる情報**: SDP（対応コーデック等）と ICE 候補
  （＝その端末の IP アドレス候補。LAN 内アドレスや、STUN で判明した外側の
  アドレスを含む）。コードを渡した相手には自分の IP アドレスが見える。
  これは P2P 接続の性質であり、コードは「見せてもよい相手」にだけ渡すもの
  として UI に明記する。
- **第三者がコードを入手した場合**: その配信へ視聴者として参加できる。
  ただし過去・未来の別の配信のコードは推測できない（コードごとに SDP と
  ICE 候補は新規生成され、暗号鍵もセッションごとに異なる）。視聴者が発行する
  リレー招待も同様で、漏れた場合の影響はそのツリーへの参加に限られる。
- CRC32 は改ざん検出ではなく誤り検出である。悪意ある改ざんへの耐性は
  WebRTC の DTLS ハンドシェイク側が担保する（相手の証明書指紋は SDP 内にあり、
  コードを正規の経路で受け取っている限り、指紋のすり替えは検出できる）。
- チャットは DataChannel 上の DTLS で暗号化されるが、ツリーの中継ノードは
  チャットを転送時に読める（中継という仕組み上避けられない）。エンドツー
  エンド暗号化は本設計の範囲外であり、その旨を README にも書く。
- XSS 対策: チャットや表示名など外部入力はすべて `textContent` で描画し、
  HTML として解釈させない。

## 10. テスト方針

- **単体テスト（Node）**: コーデックの往復一致（ランダムな SDP/ICE を含む）、
  CRC 不一致・版違いコードの拒否、プロトコルメッセージの検証、状態遷移の
  正当性、ツリー上限の判定、視聴者数の集計。アプリ本体の核ロジックは
  `nagare.html` 内の独立したスクリプトブロックに置き、テストから抽出して
  そのまま実行する（実装とテスト対象を一致させるため）。
- **実接続テスト（Electron 2画面）**: 配信ページと視聴ページを別ウィンドウで
  開き、フェイクメディアで映像を作り、コード交換を自動で行い、視聴側の映像が
  流れることとチャットの往復を確認する。リレーも1段確認する。
